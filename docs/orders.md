# NOVA Orders (Telegram + التطبيق)

الطلبات تُنشأ في **جدول واحد** (`orders` + `order_items`) تشاركه واجهات NOVA
كلها (التطبيق، البوت، الـ Mini App). المصدر الوحيد للأسعار والمخزون هو
PostgreSQL.

## تدفق إنشاء الطلب (orders.createOrder)

```text
سلة المستخدم (قراءة طازجة)
  → فحص مخزون كل سطر
  → خصم مخزون محمي (قفل تفاؤلي: eq('stock', القيمة_المقروءة))
  → توليد رقم NOVA-XXXXXX (count+1 مع إعادة محاولة عند التصادم)
  → INSERT orders (status='received', payment_method='cod')
  → INSERT order_items (snapshot: اسم/صورة/سعر/كمية/إجمالي)
  → نجاح: مسح السلة | فشل: إرجاع المخزون (+ حذف الطلب) وإبلاغ المستخدم
```

- **Snapshot الفاتورة**: تغيير المنتج لاحقاً لا يغيّر فاتورة الطلب القديم.
- **لا يُثق أبداً** بسعر أو كمية قادمة من العميل/تيليجرام/Gemini.
- خصم المخزون ليس Transaction ذرية واحدة في القاعدة (سلسلة محمية مع
  rollback) — نفس مستوى المخاطرة الحالي في التطبيق. الترقية الذرية (دالة
  Postgres) مُقترحة عند أول تزايد في الضغط.

## رقم الطلب

`NOVA-000001`, `NOVA-000002`, … — قابل للقراءة، فريد (PK)، تسلسلي مع
إعادة محاولة، وبديل زمني `NOVA-T…` عند تصادم متكرر (نظرياً مستحيل).

## حالات الطلب

| القيمة | العرض |
|---|---|
| `received` | قيد المراجعة |
| `confirmed` | مؤكد |
| `preparing` | قيد التحضير |
| `shipped` / `out_for_delivery` | في الطريق |
| `delivered` | تم التسليم |
| `cancelled` | ملغى |

⚠️ جدول `orders` الفعلي (بعد migration 001) عمود `status` فيه CHECK يقبل:
`received, confirmed, shipped, delivered, cancelled` — أي تغيير حالة من
الأدمن يجب أن يلتزم بهذه القيم (أو وسّع الـ CHECK في migration جديدة).

## جسر الإشعارات (تطبيق ↔ تيليجرام)

- الأدمن يغيّر الحالة من التطبيق → يُدرج صف في `notifications`.
- البوت يستقصي جدول `notifications` كل 30 ثانية لكل حساب مربوط، ويرسل
  الإشعار لتيليجرام مع زر «عرض الطلب».
- **لا يعلّم الإشعارات مقروءة** — شاشة إشعارات التطبيق تعمل كما هي.
- موضع التقدم: `telegram_sessions.context.lastNotifiedAt` (بلا أسرار).
- أول فحص لمحادثة جديدة: نافذة آخر 5 دقائق فقط.

## اختبارات دخان يدوية (سجل المرور)

1. طلب سليم عبر البوت → صف في `orders` + `order_items` + خصم مخزون + سلة فارغة.
2. **منع التكرار**: الضغط على «تأكيد» مرتين لا يُنشئ طلبين (حالة الجلسة
   `checkout_confirm` تُصفَّر بعد أول نجاح — الثاني يرد «لا يوجد طلب معلّق»).
3. مخزون 1 وإضافة كمية 2 → رسالة «الكمية المتوفرة هي 1 فقط» + المخزون سليم.
4. إلغاء أثناء التدفق → لا طلب، والسلة محفوظة.
5. تغيير حالة من التطبيق → إشعار في تيليجرام خلال ≤30 ثانية.
6. `get_order` لطلب مستخدم آخر (تخمين ID) → «الطلب غير موجود أو لا يعود لك».
